## Technical Decisions & Rationale

### 1. Package Manager: npm Workspaces
**Decision**: Used native `npm` workspaces rather than `pnpm` or `yarn`.
**Rationale**: The project brief emphasized making this tool as easy as running `npm install consentguard`. By using standard `npm workspaces`, we keep the developer barrier-to-entry at absolute zero. Any developer can clone the repository and run `npm install` without needing to globally install external package managers like `pnpm` first.

### 2. Bundling Strategy: Vite + Tsup
**Decision**: Selected `Vite` for the client package and `Tsup` for the server, cli, and shared packages.
**Rationale**: 
- **Vite (Client)**: The client interceptor needs to be a tiny (<5KB), optimized script that can be embedded directly into websites via IIFE or ESM. Vite (powered by Rollup/Terser) is perfect for minifying and chunking browser assets securely.
- **Tsup (Server/CLI/Shared)**: Node environments don't need complex frontend bundling. `Tsup` provides incredibly fast, zero-config TypeScript compilation directly to CommonJS and ESM, which is ideal for our Hono proxy server and shared configuration objects.

### 3. Testing Framework: Vitest
**Decision**: Chosen `vitest` over `jest`.
**Rationale**: Vitest provides out-of-the-box TypeScript support and shares configuration with Vite. Since we are using Vite for the client, keeping the test runner in the same ecosystem reduces config bloat and provides a much faster test suite execution compared to running Jest with `ts-jest`.

### 4. Base TypeScript Configuration
**Decision**: Created a `tsconfig.base.json` at the root and extended it in all workspaces.
**Rationale**: Ensures universal strict type-checking and ECMAScript compilation targets across the monorepo. It prevents configuration drift between the client, server, and cli packages, ensuring the whole codebase adheres to the same standards.

### 5. Local Infrastructure: Docker Compose
**Decision**: Added a `docker-compose.yml` to the root.
**Rationale**: The `hono` server proxy relies on `Redis 7+` for caching consent states. Providing a docker-compose file allows developers to instantly spin up an isolated, local Redis instance without cluttering their local machines, fulfilling the "easy developer experience" mandate in the project brief.
